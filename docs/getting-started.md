# Getting started

From a fresh clone to an open pull request. Every command here was run on a clean checkout before it was written down.

## Prerequisites

- Python 3.11 or newer (CI uses 3.12)
- Node 22 or newer (the frontend declares `engines.node >= 22`)
- Git and a GitHub account

You do not need any server, Netlify, or Docker access. Merging to `prod` deploys the site; contributors never touch infrastructure.

## 1. Fork and clone

Fork `seanfinchg/jobs.seanfinch.com` on GitHub, then:

```
git clone https://github.com/<your-username>/jobs.seanfinch.com.git
cd jobs.seanfinch.com
git switch dev
```

`dev` is the base for all work. Add the original repo as `upstream` if you want to pull in later changes:

```
git remote add upstream https://github.com/seanfinchg/jobs.seanfinch.com.git
git pull upstream dev
```

## 2. Backend

Use a virtual environment. From the repo root:

```
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements-lock.txt -r requirements-dev-lock.txt
pip install --no-deps -e ".[dev]"
python -m pytest
```

Expected: the whole suite passes in a few seconds, with no network access (191 tests at the time of writing; the count drifts). `.venv/` is gitignored.

The lock files pin exact versions on purpose. If `pip install` fails on a pin, tell us in an issue rather than loosening it.

The form-fill harness needs Playwright and is optional: `pip install --no-deps -e ".[dev,apply]"`. You do not need it for anything else.

Run all backend commands from `backend/`. The CLI uses relative paths (`profiles/`, `jobfinder.db`, `../frontend/public/`).

## 3. Frontend

```
cd frontend
npm ci
npm run dev        # local dev server (Vite)
npm run build      # typecheck (tsc) and production build into frontend/dist
```

`npm run lint` currently fails because no ESLint config exists yet. That is a known gap and a good first task (see [good-first-tasks.md](good-first-tasks.md)).

### Getting data for dashboard work

The dashboard reads three JSON files from `frontend/public/`. They are gitignored and generated by the backend. You do not need to run a scrape to get them. The live site publishes them, so download them:

```
cd frontend/public
curl -fO https://jobs.seanfinch.com/data.json
curl -fO https://jobs.seanfinch.com/meta.json
curl -fO https://jobs.seanfinch.com/fields.json
```

Then `npm run dev` shows real data. Their shape is documented in [data-contract.md](data-contract.md).

## 4. A safe first scrape (one board)

A full run polls well over a hundred boards, takes a long time, and must stay polite to the job boards. Do not run `jobfinder run --profile new-grad-cs` as a casual test. Instead, make a throwaway profile with a single board.

Create `backend/profiles/scratch.yaml` (the name is gitignored):

```yaml
meta:
  name: "Scratch: one board"
level: all
fields: [software-engineering]
boards:
  greenhouse:
    - {company: Datadog, token: datadog}
```

Then, from `backend/`:

```
python -m jobfinder profile show scratch     # the merged filters and boards
python -m jobfinder run --profile scratch    # one board, a few seconds
python -m jobfinder dashboard                # writes ../frontend/public/*.json from the local DB
```

On a verification run this fetched 397 postings from the board and stored 9 that passed the filters. The results land in `backend/jobfinder.db` (gitignored). Delete the DB and the scratch profile when you are done; note that `jobfinder dashboard` overwrites the three files in `frontend/public/`, so re-download the live ones afterward if you want the full data set back.

To check whether a company is on a supported ATS before adding it to a board list:

```
python scripts/discover_tokens.py "Company Name"
```

It tries slug variants against each adapter's live endpoint and prints a YAML fragment to paste. It never edits a board file itself.

## 5. Windows notes

- Use PowerShell or Git Bash. Activate the venv with `.venv\Scripts\Activate.ps1` (PowerShell) or `source .venv/Scripts/activate` (Git Bash).
- Long paths: `node_modules` can exceed the classic 260-character limit, which breaks `npm ci` cleanup and some `pip` installs. Either run `git config --system core.longpaths true` and enable Windows long paths, or clone close to a drive root such as `C:\src`.
- Line endings: the repo is LF. Shell scripts are forced to LF by `.gitattributes`. Keep your editor on LF (the `.editorconfig` does this for most editors) so diffs stay clean.
- `source` and `curl -fO` work in Git Bash. In PowerShell use `curl.exe -fO <url>` (plain `curl` is an alias for something else).

## 6. Pick a task

See [good-first-tasks.md](good-first-tasks.md) for a list with file pointers and acceptance criteria. For anything not on that list, open an issue first and say what you plan to do; small fixes can go straight to a PR.

## 7. Branch, change, test, open a PR

```
git switch dev && git pull upstream dev
git switch -c docs/fix-typo          # <type>/<short-slug>: feat, fix, docs, chore, refactor
# edit, add tests
cd backend && python -m pytest       # must pass
cd ../frontend && npm run build      # if you touched the dashboard
git add <files> && git commit        # one-line subject, 72 characters or fewer, no trailing period
git push -u origin docs/fix-typo
```

Open a pull request into `dev` on the original repo and fill in the template (bullets only). The maintainer reviews and merges every PR with a merge commit. CI for a first-time contributor needs the maintainer to approve the workflow run before it starts, so a pending check right after you open the PR is normal.

Before you push, check that your diff holds no personal data: no resume, database, `.env`, `answers.local.yaml`, credentials, or real contact details.
